## Decision

**Partial overall; not ready for a strict model-level, point-in-time training panel.** The three identified artifacts support a reproducible source-version audit and a useful candidate crosswalk. **None of the twelve audited candidates has a verified link to the exact executed checkpoint or service snapshot, generated outputs, and actual evaluation protocol.**

The strongest candidates for further work are the **three StarCoder2 base models and two DeepSeek-Coder base models**. Their pre-cutoff compute evidence is substantially better than their execution provenance. The GPT-4 and Code Llama candidates expose additional alias, variant, compute-scope, or source-conflict problems.

## 3. Declared cutoff and separate clocks

I used **T = 2024-04-20T23:59:59Z**. This is an explicit historical information cutoff for the proposed audit, not a claim that an experiment occurred then.

A consequential finding is that **A’s exact bytes already occur in ancestor commit [`ba37a9f43a5706e87762951029baab25880cd0d6`](https://github.com/evalplus/evalplus.github.io/blob/ba37a9f43a5706e87762951029baab25880cd0d6/results.json)**, timestamped **2024-04-20T03:06:04Z**.

| Time concept | Treatment |
|---|---|
| Selected snapshot A commit | April 21 publication vintage |
| Earlier byte-identical A ancestor | Pre-cutoff **repository chronology** evidence |
| A’s independently observed first-public time | **Unknown** |
| Actual inference time | **Unknown** |
| Selected snapshot B commit | Post-cutoff publication vintage |
| First availability of every B value | **Not proven**; some work was reused from earlier commits |
| Current Epoch capture and analyst derivations | 2026 evidence and processing events |

Consequently:

- **A cannot be called an unseen future target merely because the selected snapshot commit is dated April 21.** Historical labels can legitimately belong in training data, subject to an explicit repository-chronology assumption.
- **B cannot silently replace the target known at T.** It can be retained in a separately identified hindsight view.
- **B’s values are not all proved to have first appeared after T.** The selected artifact is later; per-value first-public timing was not reconstructed.
- Neither snapshot date establishes a new inference run.

The repository’s canonical `known_at` means availability **to the dataset**, not historical publication. Evidence collected in 2026 must not receive an invented 2024 ingestion timestamp. This proposal leaves that convention intact. See the pinned [dataset specification](https://github.com/mishakgg/pdoom-live/blob/720ee3cb7107cc0cb9bca8b85983df7ee8db6ddc/docs/evidence-program/dataset_spec.md).

### What can be reconstructed before T?

A dated primary source can support a historical input even when the current Epoch row cannot. The examples distinguish:

- A **source-reported value**, with its own availability evidence.
- A **new calculation from pre-cutoff inputs**, with separately recorded input availability and a 2026 `derived_at`.
- A **current-only observation**, excluded from the historical feature set.

For example, computing DeepSeek’s approximate pretraining FLOP from earlier parameter/token disclosures does not establish that Epoch published that estimate in 2024. The schema represents this distinction explicitly.

### JSON Schema design

The schema stores candidate identity and features once, with two publication snapshots underneath. Its main components are:

| Component | What it preserves or separates |
|---|---|
| `artifact_records` | URL, version, hash, byte length, retrieval, repository vintage, preservation, and redistribution status |
| `protocol_records` | Declared suite versions and nominal populations, separated from verified executed protocol |
| `identity` | Documentary candidate ID, inspected revision, executed ID, variant relationship, and evidence |
| `features` | Raw value, numeric interpretation, bounds, uncertainty label, compute scope, provenance, and cutoff eligibility |
| Feature clocks | `public_availability`, `input_information_availability`, `availability_basis`, and `derived_at` |
| `snapshots` | Four native score slots plus `link`, `open-data`, `prompted`, `size`, missingness, and revision relationship |
| `dependencies` | Training ancestry, shared measurements, reused compute, and conservative split groups |
| `decisions` | Separate descriptive, historical-training, hindsight, prospective, and independent-compute decisions |

The included-feature gate distinguishes a historical source value from a reconstruction using earlier inputs. Reconstructed values require derivation information and input dependencies. Strict analytical inclusion requires documented executed identity.

**Verification status:** exact source-value, count, uniqueness, clock-consistency, and bounded structural checks passed. Full Draft 2020-12 metaschema validation was not available in the inspected runtimes. Source truth and dependency semantics require additional checks beyond JSON Schema. The eight acceptance cases below remain proposed and unexecuted.

## 7. Dependency and family grouping rules

These are **proposed analytical rules**:

1. **Deduplicate bytes without erasing provenance.** Reimporting an identical hash and byte length adds any new receipt or source location, not a new scientific run.
2. **Separate publication identity from observation identity.** A scientific observation needs model identity, output/run identity, protocol, and metric. Unknown run IDs remain null; they do not collapse into one shared run.
3. **Keep a candidate’s metrics and vintages together.** A/B assertions and the four metrics must remain in the same split group. Equal scores do not prove shared outputs; changed scores do not prove new inference.
4. **Group documented dependencies before splitting.** Same checkpoints, reused outputs, ancestors/descendants, conversions, quantizations, and distillation relationships form indivisible components. Multi-parent models must retain links to all known parents.
5. **Use four conservative family blocks here:** GPT-4, Code Llama, DeepSeek-Coder v1, and StarCoder2. This is a precaution, not a claim that every family member shares identical weights.
6. **Represent reused compute once.** Link descendant features to the underlying estimate; distinguish ancestral pretraining, additional training, and total compute.
7. **Track other dependence separately.** Shared benchmarks, evaluators, corpora, publications, and estimate sources warrant additional clustering. Sharing a benchmark alone should not merge all models into one ancestry component.
8. **Evaluate by family and time.** Fit preprocessing and feature selection on training data only, report checkpoint/lineage counts, and test sensitivity to uncertain ancestry. Four family blocks offer little support for strong generalization claims.

## 8. Eight proposed acceptance cases

**These are specifications for a future adapter, not executed production tests.**

| Case | Attempt or fixture | Required result |
|---|---|---|
| **1. Alias versus executed model** | Assign `gpt-4-0314` from “GPT-4 (May 2023),” or infer API identity from a ChatGPT product announcement | Preserve the candidate; executed identity remains unknown without invocation/response evidence |
| **2. Base versus specialized or instruction-tuned** | Match by normalized family and size, then copy base total compute to Python/Instruct | Reject direct equivalence; preserve only evidenced ancestry and separately scoped compute |
| **3. Revision identity** | Use today’s Hub revision for an April 2024 result, or count a tokenizer/card edit as new training | Keep documentation, weights, tokenizer/config, and executed revisions distinct; prohibit backdating |
| **4. Correction versus new inference** | Treat A→B score changes as capability growth or an independent run | Preserve both vintages; require output reuse evidence for regrading and execution evidence for new inference |
| **5. Missing values and uncertainty** | Turn null into zero, forward-fill removed scores, populate a blank compute cell from notes, or convert “Likely” into a 95% interval | Preserve native blanks/nulls, notes, labels, and reported intervals; label any extraction as derived |
| **6. Future information and cutoff clocks** | Backdate current citations, call A a future outcome from its selected commit date, or silently substitute B into the T information set | Enforce feature-specific evidence; preserve repository chronology versus first-public uncertainty and separate hindsight |
| **7. Benchmark-imputed compute** | Use Turbo’s notes estimate as an independent performance predictor, even if an earlier date becomes available | Exclude it from independent compute–performance tests; temporal availability does not remove circularity |
| **8. Duplicates and dependence** | Count two snapshots as 202 independent examples or split related variants/vintages across folds | Keep artifact, candidate, checkpoint, run, metric, lineage, and family counts separate; enforce grouped, idempotent handling |
